## 1. תפקיד בסיס הידע

בסיס הידע הוא **מקור האמת היחיד** לכל טענה מקצועית של הסוכן (עיקרון 2 בפרק 1). מה שלא כתוב בו, הסוכן לא יודע.

שלוש הנחות יסוד:
1. **בסיס הידע ציבורי.** הוא יושב ב-repo הציבורי, ולכן כל מה שנכנס אליו גלוי לכל אחד, גם בלי הסוכן. זה המבחן לכל משפט: "האם אני בסדר שזה יופיע ב-GitHub?"
2. **עומק ולא רוחב.** קורות החיים כבר מכסים רוחב. הערך של התיק הוא ה"למה" וה"איך": למה היה קשה, מה נשקל ונדחה, מה נשבר.
3. **אמת שאפשר לאמת.** כל מספר בתיק הוא מספר ששרה יכולה להסביר בראיון: איך נמדד, מתי ומול מה.

**קישורי החברות (US-8.1) לא נמצאים כאן.** רשימה ב-repo ציבורי הייתה חושפת לאילו חברות שרה פונה. הם נשמרים ב-Neon ומנוהלים בסקריפט פרטי. ראי סעיף 10.

## 3. סכמת רשומת פרויקט

כל רשומה היא קובץ Markdown עם frontmatter. ה-frontmatter נבדק אוטומטית ב-CI, וגוף הרשומה בנוי מכותרות קבועות.

### Frontmatter

```yaml
id: postgres-rls-backbone            # קבוע, באנגלית, לא משתנה אחרי פרסום
type: project                        # project | experience | profile | skills | faq | ...
title: { en: "...", he: "..." }
aliases: ["RLS", "הרשאות ברמת שורה"] # מילים שאנשים ישתמשו בהן בשאלה, בשתי השפות
period: "2026"
experience: ainsof-capital           # קישור לרשומת התפקיד, אם יש
role: "Sole engineer"
tech: [PostgreSQL, Supabase, RLS]
tags: [databases, security, backend]
metrics:                             # רק מספרים ששרה יכולה להסביר
  - label: "API latency"
    before: "582ms"
    after: "40ms"
    how_measured: "..."              # חובה. בלי זה, המספר לא נכנס
architecture:                        # בסיס לדיאגרמה (US-6.2). המודל לא ממציא רכיבים
  components: [{ id: api, label: "REST API" }, { id: db, label: "PostgreSQL" }]
  edges: [{ from: api, to: db, label: "RPC + RLS" }]
code_allowed: false                  # האם מותר לצרף קטעי קוד
depth: full                          # full | overview. ראי סעיף 5
related: [claims-trust-model]
answers:                             # שאלות שהרשומה עונה עליהן. בסיס ל-golden set
  - "How did she secure multi-tenant data?"
  - "איך היא שיפרה ביצועים של API?"
review:
  approved: true                     # רשומה בלי אישור לא נקלטת
  approved_on: 2026-11-10
  publication_check: "employer-ok"   # employer-ok | own-project | anonymized
```

### גוף הרשומה

| כותרת | מה כותבים | חובה |
|---|---|---|
| `## Problem` | מה היה צריך לפתור, ולמי | כן |
| `## Why it was hard` | האילוצים, ומה הפך את זה ללא טריוויאלי | כן |
| `## My role` | מה שרה עשתה בעצמה, בנפרד ממה שעשו אחרים | כן |
| `## Architecture` | רכיבים, זרימת נתונים, ולמה נבנה כך | כן |
| `## Decisions and alternatives` | 2 עד 4 החלטות. לכל אחת: מה נבחר, מה נדחה ולמה | כן |
| `## What broke` | תקלה משמעותית אחת: איך זוהתה, מה הייתה הסיבה, איך תוקנה | מומלץ |
| `## Results` | תוצאות עם מספרים, ואם אין, תוצאה איכותית ברורה | כן |
| `## In hindsight` | מה היא הייתה עושה אחרת היום | מומלץ |

כל כותרת היא גם יחידת חיתוך (chunk) ברירת מחדל, עם מזהה יציב `<id>#<section>`, למשל `postgres-rls-backbone#decisions`. הציטוטים בתשובות מצביעים על המזהה הזה. פרק 5 יבדוק אם חיתוך אחר עובד טוב יותר.

## 4. שפת הכתיבה

**ההמלצה:** גוף הרשומה באנגלית, והשדות `title` ו-`aliases` בשתי השפות.

- רוב המונחים הטכניים באנגלית ממילא, וקורות החיים באנגלית.
- כתיבה כפולה של כל רשומה הייתה מכפילה את העבודה, ויוצרת סיכון ששתי הגרסאות לא יהיו זהות.
- **הסיכון:** שאלה בעברית מול תוכן באנגלית. חיפוש מילים לא ימצא התאמה, ו-embeddings רב-לשוניים יעזרו רק בחלק מהמקרים. `aliases` בעברית הם הפתרון הראשון, ופרק 5 יבדוק גם תרגום של השאלה לפני החיפוש.
- **ההחלטה הסופית תתקבל לפי מספרים:** ה-golden set יכלול שאלות בשתי השפות, ונמדוד Recall בנפרד לכל שפה. אם העברית חלשה בהרבה, נשקול סיכום בעברית לכל רשומה.

## 6. כישורים מקושרים להוכחות

כישור יכול להגיע מעבודה בפועל או מלימודים. לכן לכל כישור ב-`skills.md` יש רמת הוכחה, והסוכן מנסח את התשובה לפיה:

```yaml
- name: pgvector
  level: used           # שימש בפרויקט שיש עליו רשומה
  evidence: [clip-embeddings-kafka]
- name: Java
  level: studied        # נלמד בתוכנית לימודים או בקורס
  evidence: [education]
  note: "..."           # אופציונלי: מה נלמד או נבנה, למשל פרויקט גמר
- name: Kubernetes
  level: listed         # מופיע בקורות החיים, בלי פירוט נוסף
  evidence: []
```

| רמה | איך הסוכן עונה |
|---|---|
| `used` | מתאר את השימוש ומצטט את הרשומה |
| `studied` | "היא למדה את זה במסגרת..." ולא מציג את זה כניסיון בעבודה |
| `listed` | "זה מופיע בקורות החיים שלה, אבל אין לי פרטים נוספים. כדאי לשאול אותה ישירות." |

**ההבחנה בין רמות היא לא חולשה.** ההפרדה בין "עבדתי עם זה" ל"למדתי את זה" היא בדיוק מה שמהנדס בכיר מחפש, והיא מראה שהמערכת לא מנפחת. גם בהתאמה למשרה (US-5.1), כישור ברמת `studied` מוצג כהתאמה חלקית ולא כחזקה.

לפי קורות החיים, כישורים שעדיין אין להם הוכחה בפרויקט: Java, C#, C++, .NET Core, MongoDB, DynamoDB, SQL Server, MySQL, Kubernetes, AWS S3. **שרה תבדוק** מה מהם נלמד בלימודים (`studied`) ומה רק מופיע ברשימה (`listed`).

## 7. ראיון להמרת החומרים הגולמיים

לכל פרויקט: אני מכין טיוטה מהחומרים הגולמיים ומקורות החיים, ומסמן את הפערים. אחר כך שרה עונה רק על מה שחסר, ואני משלים.

**שאלות לכל פרויקט**
1. מה היה המצב לפני, ומי סבל ממנו?
2. מה הפך את זה לקשה? מה היה האילוץ הכי מגביל?
3. מה עשית לבד, ומה עשו אחרים?
4. ציירי במילים את הרכיבים ואיך הנתונים זורמים ביניהם.
5. מה ההחלטה הכי חשובה שקיבלת? מה עוד שקלת, ולמה לא?
6. מה נשבר? איך גילית, מה הייתה הסיבה, ואיך תיקנת?
7. איך מדדת את התוצאה? (לכל מספר: מתי, מול מה ובאיזה כלי)
8. מה היית עושה אחרת היום?
9. מה מותר לפרסם, ומה לא?

**שאלות לפרופיל ול-`preferences.md`**
- איך היית מתארת את עצמך במשפט אחד למהנדס בכיר, ובמשפט אחד למגייסת?
- אילו תפקידים מעניינים אותך? (הוחלט: כל הסוגים. האם יש סדר עדיפויות?)
- עבודה מרחוק, היברידית או מהמשרד? אזור?
- זמינות להתחלה?

**אנונימיזציה:** כשפרויקט מעניין אבל רגיש, אפשר לכתוב אותו בלי שם המעסיק והמוצר, למשל "פלטפורמת ממשל נתונים בחברת השקעות". הסימון במקרה כזה הוא `publication_check: anonymized`.

**קורות החיים להורדה:** הוחלט להעלות את הגרסה המלאה, עם הטלפון והמייל. זו בחירה מודעת: הקובץ פתוח לכל מבקר באתר. הטלפון עדיין לא נכנס לבסיס הידע, ולכן הסוכן לא מקריא אותו בשיחה, וקורות החיים מוצעים רק כקובץ להורדה.

## 9. צנרת הקליטה

```
portfolio/*.md
  -> בדיקת סכמה (Pydantic): שדות חובה, review.approved, how_measured לכל מספר
  -> בדיקת פרסום: רשימת מונחים אסורים (שמורה כ-secret ב-CI, כי גם היא רגישה)
  -> חיתוך לפי כותרות, ומזהה יציב לכל קטע
  -> embeddings (אם יש מודל חינמי, פרק 5)
  -> upsert ל-Neon לפי hash של התוכן, כך שרק קטעים שהשתנו מתעדכנים
  -> הרצת ה-golden set (פרק 4). ירידה במדדים חוסמת
```

- הקליטה רצה ב-CI על כל שינוי ב-`portfolio/`.
- רשומה שנכשלת בבדיקה חוסמת את ה-merge, עם הודעה שאומרת בדיוק מה חסר.
- כל קטע במסד שומר את ה-commit שממנו נקלט, כך שאפשר לדעת מאיזו גרסה של התיק הגיעה תשובה.
