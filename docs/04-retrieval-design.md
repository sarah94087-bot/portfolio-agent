## 1. מה הפרק קובע, ומה לא

הפרק **לא בוחר** שיטת שליפה. הוא מגדיר אילו שיטות נבדקות, באיזה סדר, ולפי איזה כלל מכריעים. הבחירה עצמה מתקבלת ב-M3, לפי המספרים, ונרשמת ב-ADR.

זו ההבחנה שהופכת את עמוד התווך הראשון לאמיתי. "השתמשנו ב-hybrid search" הוא משפט שכל אחד יכול לכתוב. "בדקנו ארבע שיטות על 85 שאלות, וזה מה שיצא" הוא משפט שמעטים יכולים לכתוב.

## 2. אילוצים

| אילוץ | משמעות |
|---|---|
| **מאגר קטן** | כ-15 רשומות, ובערך 100 עד 150 קטעים |
| **שפה מעורבת** | התוכן באנגלית, וחלק גדול מהשאלות בעברית |
| **חינם בלבד** | כל מודל embeddings או reranking צריך להיות זמין בחינם, **גם בזמן שאילתה** מתוך serverless |
| **מסד אחד** | Neon Postgres עם `pg_trgm` ו-`pgvector`. בלי שירות חיפוש נוסף |
| **תקציב זמן** | השליפה מקבלת עד 300ms ב-p50, מתוך יעד TTFT של 2 שניות |

**השלכה חשובה של האילוץ השלישי:** אפשר להריץ מודל embeddings מקומי ב-CI בזמן הקליטה, אבל את השאילתה צריך להמיר לווקטור **באותו מודל** בזמן אמת, מתוך פונקציית serverless. מודל שאי אפשר לקרוא לו מ-API חינמי לא נכנס לבדיקה.

## 3. ארבעת צירי הניסוי

### ציר A: חיתוך (chunking)
| מזהה | שיטה | השערה |
|---|---|---|
| **C1** | קטע לכל כותרת ברשומה (ברירת המחדל מפרק 3) | יחידות משמעות טבעיות, וציטוטים ברורים |
| **C2** | C1, ובראש כל קטע כותרת הקשר: שם הרשומה, `aliases` ו-`tech` | קטע כמו "Decisions" לבדו לא אומר על איזה פרויקט מדובר. הכותרת אמורה לשפר בעיקר עברית ושאלות `multi_hop` |
| **C3** | חלונות קבועים של כ-300 טוקנים עם חפיפה של 50 | קו בסיס מקובל להשוואה |
| **C4** | רשומה שלמה כקטע אחד | במאגר כל כך קטן, אולי זה פשוט מספיק |

### ציר B: שיטת שליפה
| מזהה | שיטה |
|---|---|
| **R1** | מילים: `tsvector` בתצורת `simple`, ו-`pg_trgm` על הטקסט ועל ה-`aliases` |
| **R2** | וקטורים: embeddings רב-לשוניים ו-`pgvector` (cosine) |
| **R3** | היברידי: R1 ו-R2 ממוזגים ב-Reciprocal Rank Fusion, עם k = 60 |
| **R4** | R3 ואחריו reranking על 20 המועמדים הראשונים |

### ציר C: עיבוד השאילתה
| מזהה | שיטה | עלות |
|---|---|---|
| **Q0** | השאלה של המבקר כמו שהיא | אפס |
| **Q1** | הסוכן מנסח את השאילתה בעצמו, כפרמטר של הכלי `search_portfolio`. סכמת הכלי מבקשת שאילתה באנגלית, עם מונחים מפורשים | **אפס**, כי זו אותה קריאה למודל |
| **Q2** | Q1, ובנוסף 2 ניסוחים חלופיים, עם מיזוג תוצאות | קריאה ארוכה יותר, ולכן יותר טוקנים |

**Q1 הוא הרעיון המרכזי לבעיית העברית.** הסוכן ממילא מחליט מה לחפש. אם סכמת הכלי מבקשת ממנו לנסח את השאילתה באנגלית, התרגום מגיע בלי קריאה נוספת, ובלי זמן נוסף. Q1 פותר גם שאלות המשך כמו "ומה היה הכי קשה שם?", כי הסוכן מחליף את "שם" בשם הפרויקט.

**לכן מודדים שני מצבים:** Q0 בודק את השליפה עצמה. Q1 בודק את השליפה כפי שהיא פועלת באמת בתוך הסוכן. כדי שהתוצאות יהיו ניתנות לשחזור, השאילתות שהסוכן ניסח נשמרות פעם אחת ומשמשות בכל ההרצות.

### ציר D: מודלים
| תפקיד | מועמדים (חינמיות וזמינות ייבדקו ב-M1) |
|---|---|
| **Embeddings** | **נבחר ב-M3 (ADR-0009).** Gemini החינמי אסור באפליקציה שפתוחה למבקרים מאירופה. המועמדים: מודל רב-לשוני פתוח שרץ בפונקציה, או ספק שהתנאים החינמיים שלו מתירים שימוש ציבורי. `gemini-embedding-001` נשאר נקודת ייחוס בניסויים בלבד |
| **Reranking** | reranking בעזרת מודל שפה: Groq מקבל את השאלה ו-20 מועמדים, ומחזיר סדר חדש. cross-encoder רב-לשוני רק אם יש לו API חינמי |

## 4. סדר הניסויים

ניסוי של כל הצירופים (4 × 4 × 3) היה עולה מכסה רבה, ורוב הצירופים לא מעניינים. לכן הניסויים נעשים בשלבים, וכל שלב מקבע את המנצח הקודם:

| שלב | מה משתנה | מה קבוע | שאלה |
|---|---|---|---|
| **1** | C1 עד C4 | R1 ו-R2 בנפרד, Q0 | איזה חיתוך עובד הכי טוב? |
| **2** | R1 עד R3 | החיתוך הטוב, Q0 | האם היברידי מצדיק את עצמו? |
| **3** | Q0 עד Q2 | החיתוך והשיטה הטובים | כמה Q1 משפר בעברית? |
| **4** | עם R4 ובלעדיו | כל השאר | האם reranking שווה את הזמן ואת המכסה? |
| **5** | כלום | התצורה הסופית | **הרצה אחת** על `test`, לדוח הרשמי |

- כל השלבים רצים על `dev` בלבד (פרק 4, סעיף 2).
- שלבים עם רכיב לא דטרמיניסטי (Q2, R4) רצים 3 פעמים.
- לכל תצורה מדווחים: Recall@3/5/10, MRR, nDCG@5, latency ב-p50 ו-p95, וקריאות API לשאילתה. הכול בנפרד לעברית, לאנגלית ול-`cross_lingual`.

## 5. כלל ההכרעה

> **בוחרים בתצורה הפשוטה ביותר שאינה גרועה באופן מובהק מהטובה ביותר.**

- "טובה ביותר" נקבעת לפי Recall@5 הכולל, ובתנאי שהיא עוברת את סף העברית מפרק 4.
- "גרועה באופן מובהק" לפי ההשוואה המזווגת מפרק 4, סעיף 5: רווח הסמך של ההפרש לא כולל אפס.
- "פשוטה" לפי הסדר: פחות רכיבים, פחות קריאות API, פחות זמן.

**המשמעות:** אם R1 לבדו מגיע לאותה תוצאה כמו R4, נבחר R1. זה עלול להישמע פחות מרשים, אבל ממצא כמו "במאגר בגודל הזה, היברידי לא משפר באופן מובהק, ולכן ויתרנו עליו" הוא בדיוק סוג ההחלטה שמהנדס בכיר מחפש. כל רכיב שנכנס מגיע עם מספר שמצדיק אותו.

## 6. עברית

| בעיה | פתרון |
|---|---|
| ל-Postgres אין מילון עברי (stemming) | תצורת `simple` ו-trigrams |
| תחיליות צמודות (ו, ה, ב, ל, מ, ש, כ) | trigrams מוצאים התאמה חלקית, ו-Q1 עוקף את הבעיה כי השאילתה באנגלית |
| אותיות סופיות (ך ם ן ף ץ) | נרמול לאותיות רגילות לפני בניית trigrams, גם בקליטה וגם בשאילתה |
| ניקוד וסימני כתיבה | הסרה בנרמול |
| שאלה בעברית מול תוכן באנגלית | `aliases` בעברית, embeddings רב-לשוניים ו-Q1 |

## 8. החוזה מול הסוכן

`search_portfolio` מחזיר לכל היותר 5 קטעים, ולא יותר מ-3,000 טוקנים בסך הכול:

```json
{
  "query_used": "human review before machine translation overwrites",
  "results": [
    {
      "chunk_id": "human-gated-translation#decisions",
      "record_title": "Human-gated AI translation pipeline",
      "section": "Decisions and alternatives",
      "text": "...",
      "rank": 1,
      "scores": { "lexical": 0.41, "vector": 0.83, "rrf": 0.032, "rerank": null }
    }
  ],
  "candidates_considered": 20,
  "candidates": [
    {
      "chunk_id": "human-gated-translation#decisions",
      "record_title": "Human-gated AI translation pipeline",
      "excerpt": "...",
      "scores": { "lexical": 0.41, "vector": 0.83, "rrf": 0.032, "rerank": null },
      "selected": true
    }
  ],
  "latency_ms": { "lexical": 12, "vector": 140, "fusion": 1 }
}
```

- `candidates` הם כל המועמדים לפי סדר המיזוג, עם קטע קצר (עד 140 תווים) במקום הטקסט המלא, ו-`selected` למי שהועבר למודל. הם רק בחלון המעקב: המודל קורא את `results` בלבד.

- `scores.rerank` הוא המקום שמודל הדירוג נתן לקטע (מ-1), ו-`null` אם לא דורג. ב-trace נוספים `method` (‏R1, ‏R3 או R4, מי שקבע את הסדר בפועל) ו-`rerank` עם המודל, הטוקנים והסיבה לחזרה לסדר של R3, אם הייתה (ADR-0014).
- `chunk_id` הוא המזהה שהסוכן מצטט, והשרת מוודא שהוא קיים (פרק 4, תקינות ציטוטים).
- `scores` ו-`latency_ms` מוצגים בחלון המעקב (US-4.2, US-4.3), ולכן הם חלק מהחוזה ולא רק לוג.

## 9. דוח הניסויים

- **מיקום:** `docs/experiments/retrieval-<date>.md`, וה-JSON הגולמי ב-`evals/results/`.
- **מבנה:** השערה, תצורות, טבלת תוצאות עם רווחי סמך, גרף לכל שלב, החלטה ונימוק.
- **פרסום:** הדוח מוצג בעמוד האיכות (US-9.2), וכל מספר בו ניתן לשחזור בפקודה אחת (US-9.6).
- **ADRs שייכתבו בעקבותיו:** שיטת החיתוך, שיטת השליפה, מודל ה-embeddings, ועיבוד השאילתה.

## 10. סיכונים

| סיכון | מה עושים |
|---|---|
| **המאגר קטן מדי, וכל השיטות מגיעות לתקרה** (Recall קרוב ל-1). ההשוואה לא מראה כלום | הקטגוריות הקשות ב-D1 (`cross_lingual`, `multi_hop`, ניסוח שונה מהרשומה) נועדו בדיוק לזה. אם עדיין יש תקרה, מדווחים על כך בכנות, וזה עצמו ממצא |
| **אין embeddings חינמי לזמן שאילתה** | R2 עד R4 יוצאים מהניסוי, ו-Q1 הופך לכלי המרכזי לעברית. מתועד ב-ADR |
| **reranking מוסיף יותר מדי זמן** | מודדים את הזמן בשלב 4, וכלל ההכרעה כולל אותו |
| **השאילתות שהסוכן מנסח (Q1) משתנות מהרצה להרצה** | שומרים אותן פעם אחת לניסוי, ובודקים יציבות ב-3 חזרות |
| **התאמת יתר ל-`dev`** | רק תוצאות `test` מתפרסמות, ורק אחרי שהתצורה נקבעה |

## 11. החלטות ושאלות פתוחות
