# ADR-0007: registry אחד לכלים, והרצה בתוך התהליך במקום דרך MCP

| | |
|---|---|
| **סטטוס** | התקבל (5.11.2026) |
| **נשען על** | `docs/05-architecture.md`, סעיפים 2 ו-5. ‏`docs/06-agent-design.md`, סעיף 3. הקוד: `tools/registry.py`, ‏`tools/portfolio.py` |
| **אישרה** | שרה |

## הקשר
לסוכן יש כלים: חיפוש בתיק, פרויקט לפי מזהה, ובהמשך גם התאמה למשרה וטיוטת פנייה. הפרויקט חושף את אותם כלים גם לסוכנים חיצוניים דרך `/mcp` (קריאה בלבד). אפשר לחבר את הסוכן עצמו לכלים דרך MCP, כלקוח של השרת שלנו. אפשר גם להריץ אותם ישירות בתהליך.

## החלטה
**כל כלי מוגדר פעם אחת ב-registry אחד.** ההגדרה כוללת: שם, תיאור, פרמטרים ב-Pydantic, handler, והשפעה (`read`).
- **הסוכן קורא לכלים בתוך התהליך**, דרך `Registry.call`: אימות הפרמטרים, הרצה, ותוצאה בשני מבטים. `model_view` הולך למודל, ו-`trace_view` הולך למעקב.
- **`/mcp` יהיה שכבה דקה מעל אותו registry**, כשייבנה. הסכמות שלו נגזרות מאותן הגדרות.
- **קריאה לכלי אף פעם לא זורקת חריגה.** כלי לא מוכר, פרמטרים לא תקינים או כשל בהרצה חוזרים כתוצאה עם שגיאה, והמודל יכול לתקן בסבב הבא.

## השלכות
- **כלי מוגדר פעם אחת ונבדק פעם אחת.** הסוכן ו-`/mcp` לא יכולים לחשוף גרסאות שונות של אותו כלי.
- **אין קפיצת רשת בכל קריאה לכלי.** החיפוש רץ על אותו חיבור למסד כמו הבקשה. ב-MCP היה נוסף סבב HTTP, ובפונקציה של Vercel אולי גם cold start שני.
- **ערכים שנקבעים בזמן ריצה** (למשל ה-enum של מזהי הפרויקטים ב-`get_project`) נבנים מהתיק בכל בקשה, ולכן המודל רואה רק מזהים שקיימים.
- **שני מבטים על כל תוצאה:** המודל מקבל טקסט קצר ותקציב של 3,000 טוקנים, והמעקב מקבל ציונים, שיטה וזמנים. כך אפשר להראות את השליפה בלי לשלם עליה בהקשר.
- **ה-handlers לא עוברים דרך MCP בבדיקות.** כש-`/mcp` ייבנה, צריך בדיקה אחת שמוודאת שהסכמות שהוא חושף זהות לאלה שהסוכן רואה.

## חלופות שנדחו
- **הסוכן כלקוח MCP של השרת שלנו:** אותו קוד, אבל עם סבב רשת, סריאליזציה ונקודת כשל נוספת בכל קריאה, בלי שום יתרון למבקר.
- **הגדרות נפרדות לסוכן ול-`/mcp`:** שני מקורות אמת שעלולים להתרחק זה מזה.
